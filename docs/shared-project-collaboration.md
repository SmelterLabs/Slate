# Shared project collaboration

A project is a **private section**, not a second workspace or a separate hierarchy. The section home links its accessible lists (Work/Ideas are ordinary lists), section/list docs, the section's discussion channel, participant identities and an optional external whiteboard. No lists, agents or outbound messages are created automatically.

## Invitation and browser-session contract

- Owner/admin **with an unlimited admin-scope token** opens a private section's **Share → Invite a project guest**. The UI explicitly names the section and fixes **Guest · Edit**. New accounts are persons with the guest role; an existing active guest person can be re-invited by handle. Existing privileged/agent/disabled accounts cannot be invited. Existing display names are not silently changed.
- `POST /api/v1/invitations` issues a 256-bit random secret, stored only as SHA-256, with seven-day expiry. It returns the secret once. Copy the link and send it privately yourself. There is no mail integration and no claim of email/identity verification: anyone holding the link can accept it.
- The link uses `#/invite?secret=…`, never a query/path sent to the server. The board removes the fragment secret with `history.replaceState` before rendering, including when opened in an already-running tab. The acceptance button POSTs it in the body with the browser request header. Do not configure a proxy/APM to log request bodies or Cookie/Authorization headers.
- Acceptance is explicit, single-use, and checked again under the process-wide service writer lock. Granting section edit, consuming the invite and issuing its session are one transaction through `apply_change`, attributed to the accepting guest. Concurrent real HTTP attempts are tested: exactly one succeeds. This uses Slate's **one process/one worker** deployment contract; do not run multiple independent writers assuming the in-process lock is distributed.
- The browser session is an ordinary hashed Slate token with `write` scope, a `{"level": "edit"}` limit and a 30-day absolute expiry (`tokens.expires_at`). The limit caps the level only; it pins no section. A guest's reach is therefore exactly the account's shares (role `guest` sees nothing unshared, `access.compute()` adds nothing), so a section shared with the guest later shows up in `GET /me` and `GET /sections` with no new link, and the live stream reloads on the `share.*` event as for any access change (`tests/test_guest_sessions.py`). Its credential is only an **HttpOnly, SameSite=Strict, host-only cookie** at `/api/v1`, Secure on HTTPS; the cookie's `max-age` (30 days) is the browser's ceiling, and `GET /me` re-sets it on every board load so an extended session is not lost to a cookie that aged out. Local storage contains only `@browser-session`, not the token. Bearer tokens and token sign-in work alongside it, with their own expiry (null = no expiry).
- **The end date is visible and announced.** `GET /me` carries `session_expires_at` for a cookie session (null for bearer tokens); the sidebar footer shows "Access ends <date>" to the guest. Three days before, the scheduler hook `service/sessions.py:notify_expiring` records `session.expiring` once for the guest and once for the inviter (`invitations.created_by`), inbox reason `access`, pushed by default; `tokens.expiry_notified_at` (migration `b7c2d9e4f1a3`) makes it idempotent across restarts and re-arms after an extension.
- **Extend and re-issue (admin).** `POST /invitations/{id}/extend` moves the accepted session's `expires_at` to thirty days from now (`session.extended`; 422 before acceptance, 410 once cancelled or signed out). `POST /invitations/{id}/reissue` mints a fresh single-use secret for the same guest and section (a new `invitations` row, `after.reissued_from`), for another device or a link that was opened inside a messaging app; the original stays valid until used, cancelled or expired. `GET /invitations` rows carry `session_expires_at` / `session_revoked_at`. The board's invite panel has **Extend 30 days** and **Copy a link for another device** on each row.
- **The installed app signs a guest in** from a pasted invitation link: the token box accepts a whole `#/invite?secret=` link or the bare `invite_…` secret (`lib/collaboration.ts:inviteSecretFrom`) and `board.signIn` then calls `POST /invitations/accept` in cookie mode instead of treating it as a bearer token. Each device still needs its own single-use link; the invite screen and the inviter's copy dialog say so, and say to open the link in Safari or Chrome rather than inside a messaging app.
- Browser writes require `X-Slate-Client: browser`; supplied Origin must exactly match the request origin; cross-site fetch metadata is refused. No cross-origin cookie API is enabled. All fetch/upload/download helpers understand cookie mode; EventSource uses the cookie without a token query. Bearer headers and the EventSource `token=` query serve token sign-in.
- Acceptance has independent, bounded in-process limits: ten attempts per direct client address per minute, 100 globally, at most 1,024 address buckets. Forwarded IP headers are not trusted to bypass this. A reverse proxy/NAT shares a bucket. Restart clears buckets; this is not a distributed rate limiter.
- Sign out revokes the browser token server-side and deletes the cookie, then reloads to discard scoped stores. After logout/expiry, an admin issues a fresh invite: there is deliberately no password, emailed magic-link delivery or identity-recovery service. An existing guest can be invited to the same section again.
- Cancel an invitation to revoke that invite **and the session it issued**. Removing the person's share ends that section access across all their tokens. These are separate controls: cancelling one invite does not silently erase a pre-existing share or revoke unrelated credentials. To completely offboard, remove shares and disable the account/revoke its tokens using the Members controls. Already-downloaded information cannot be recalled.
- Behind a TLS-terminating proxy (for example Tailscale Serve or Caddy → the container over the Docker bridge) uvicorn only sees `https` and the browser's real address when it trusts the proxy's `X-Forwarded-*` headers: `deploy/server/compose.yml` sets `FORWARDED_ALLOW_IPS=*` because only a process on the host (the proxy) can reach the loopback-published port. Without it the cookie is not `Secure`, the same-origin check compares against an `http://` base URL and refuses every browser write, and the acceptance limiter buckets everyone under the bridge address.
- Use a trusted protected connection (prefer HTTPS, which sets Secure) before sharing a real invitation. HTTP remains available for local/private-network deployments and isolated tests; it is not internet-safe transport.

## Authorization and event details

Migration `d41b0c8e2a19` follows `3c8a1e5f7b20`: `invitations`, nullable token expiry, browser-session marker, nullable section whiteboard URL. Invitation hashes are excluded by `SECRET_COLUMNS`; no secret is recorded in events. The event types are `invitation.created`, `invitation.accepted`, `invitation.revoked`, `session.created`, `session.expiring` and `session.extended` (migration `b7c2d9e4f1a3`, `tokens.expiry_notified_at`), and `section.participants_changed`. The last is a payload-free, section-scoped signal to refresh participants after section share changes or invitation acceptance; it does not broadcast another user's share records.

`service/collaboration.py` owns invitation lifecycle/validation and project participant metadata; `api/collaboration.py` is the REST adapter and cookie/attempt boundary. No provider or agent-product coupling. The service access filters apply equally to REST, local/HTTP MCP and atomic batch operations.

Section editors can create lists inside that section. List creation extends the request's access snapshot immediately after the authorized insert, so its default statuses and subsequent same-batch operations succeed. This does not bypass checks or let list-only guests create siblings. Guests/limited tokens cannot change global section positions, even if they edit that section.

Event reads do not retain arbitrary scoped content merely because the viewer authored it. Live gates recheck account/token revocation and expiry before delivery, and replay pages reauthenticate. A live stream closes on revoked credentials or narrowing of reach, including when the stream's type filter would otherwise skip the revocation event. Cookie browsers reauthenticate/reload to discard revoked doc/chat/blob caches. Attachment/doc-file HTTP responses are `no-store`.

Project participants expose names, handles, kinds and section access levels, not preferences/token metadata/global presence. Scoped roster/export identity directories include reachable participants, not unrelated accounts; scoped rosters redact global online/last-seen/stream/throttle/wake telemetry. Scoped event counts and assignments are filtered. Whiteboard URLs are returned by the authorized project endpoint, not to list-only users through section heading metadata. Section-only event fields are likewise not exposed to list-only heading viewers.

Whiteboard storage accepts only HTTPS URLs with a host and without credentials, whitespace, backslashes or invalid ports. Empty string clears it. The UI validates again and uses an external anchor with `noopener noreferrer` and no-referrer; Slate does not fetch it. External access is managed separately, not inherited from the Slate share.

## The project's agent

Sharing an agent into the section (Share dialog, a `shares` row for the agent account) gives its guests the agent's chat (`agent:<id>`) **from the moment of that share on**: messages before it, including the owner's private conversations with the agent, stay out of reach for guests and section-limited sessions (the read filter, the live stream and the audit log agree; revoking and re-granting the share moves the line forward). Members, admins and the agent itself keep the whole history.

Guests can post in that chat. **Guest-role project agents wake only on an explicit `@handle`**, whether the sender is a guest or the owner. Plain conversation, mentions to others and untagged follow-ups (including threads) do not wake them; an edit that adds their mention does. Workspace agents with non-guest roles retain implicit direct-chat addressing. When addressed, the agent acts with **its own token**. A project agent that guests can drive must therefore hold a token limited to the project (`limit: {"section_ids": [section]}` or the project's lists, minted on the agent's account): with an unlimited token, a guest's "move everything in Secret to done" would reach the owner's private lists. Mint the limited token before sharing the agent; the agent's own chat and check-in work the same on a limited token.

## Sidebar

The five primary entries are **My Work, Inbox, Docs, Chat, Everything**. All other navigation entries live under an accessible **More** disclosure, keeping their role/access conditions. Expansion preference is local to this browser **and account**. Opening a secondary deep link expands More and labels it with the selected destination; collapsing it still identifies that destination. Selecting an entry closes the phone drawer.

Drag a section heading above/below another heading to reorder entire sections. A distinct drag type prevents collision with list dragging. Drop indicators show placement. **⋯ → Move up / Move down** is the keyboard/touch fallback. Both use atomic `/batch` section position updates, the ordinary service events, and readback; reload and second boards retain ordering. Lists never change section during a section drag. Guests/limited tokens get no drag or enabled section-order controls.

## Test coverage and limitations

Tests exercise invitation expiry/replay/concurrent acceptance/cancellation/session logout/expiry, CSRF and attempt bounds; scoped list creation and global reorder refusal; REST/MCP/batch item/doc reads and writes, search, doc versions/files, item attachments, participant/roster/export metadata, notifications and revoked access; real cookie SSE replay/live delivery/filtering and stream closure. Browser tests exercise admin creation, guest acceptance, cookie reload, project/docs/discussion links, saved whiteboard, sign-out/replay, share revocation while a doc is open, desktop drag with a second board and reload, keyboard More, account-local preference, deep-link discovery and touch-menu ordering/phone layout.

**Global catalogs are not a private namespace:** tags and doc templates are workspace-wide. A guest or section-limited session (`tests/test_guest_scope.py`) lists only the tags on tasks and docs it can reach plus the ones it made, and only an owner or admin renames, recolours, merges or deletes a tag; workspace-wide automations (with their webhook URLs), saved views outside the guest's scope and doc tags on unreachable docs are absent for it. Tag *names* a guest can reach are still the workspace's words: do not put customer/private information in global taxonomy names/options. Section sharing is access control inside one trusted workspace, not multitenancy.

The tests use synthetic accounts and isolated databases; they do not exercise a deployed reverse proxy or TLS configuration, so check cookie transport on your own deployment.
